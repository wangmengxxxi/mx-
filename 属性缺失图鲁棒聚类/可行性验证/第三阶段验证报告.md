# 第三阶段可行性验证：SDCN 校准与 AMGC CPU 收敛检查

日期：2026-10-22。目标是确认 SDCN 小范围校准可以稳定运行，并确认 AMGC 的关键依赖、数据读取和训练主循环可以在本机执行。正式的多掩码、多种子实验只有在两个运行门槛都满足后才启动。

## 结论

本阶段确认了“属性缺失图鲁棒聚类”方向具备实现条件：SDCN 和 AMGC 都能在现有 Python 3.9、PyTorch 2.8 CPU 环境运行，Cora 数据顺序和图边与本地 Planetoid 原始文件一致，训练损失保持有限，模型输出可保存并复核。另行建立了 CUDA PyTorch 环境，但该环境目前未通过 CUDA 张量分配测试，不能用于训练。

本阶段不启动 5 掩码 × 3 种子扩大实验。原因是 SDCN 在 80% 缺失的 Zero 填充下仍出现退化（NMI 约 0.04、ARI 约 0、最大簇占比约 0.89），而 AMGC 的 100 epoch 检查虽显示训练稳定、预测趋稳，指标后期仍有提升，且只完成官方 1000 epoch 调度周期的 10%。继续完成固定掩码长周期验证，再决定是否扩大。

## SDCN 校准

脚本：`run_sdcn_baseline.py`。小范围配置为隐藏层 128,64，预训练 100 epoch，联合训练 400 epoch，学习率 1e-3，0% 和 80% 缺失，Zero/FP，三种子 0、1、2；结果目录为 `sdcn_stage3_small_lr1e3/`。

在 80% 缺失下，三种子最终结果如下：

|填充|ACC|NMI|ARI|占用簇数|判断|
|---|---:|---:|---:|---:|---|
|Zero|0.302–0.307|0.040–0.069|约 0|6–7|持续退化|
|FP|0.427–0.482|0.258–0.347|0.156–0.246|7|可运行，仍需优化|

为接近论文原始宽度，另做 `500,500,2000`、预训练 30、联合 100、seed 0 的宽结构探针，结果目录为 `sdcn_stage3_wide_probe/`。80% 缺失 FP 最终 ACC 0.496、NMI 0.319、ARI 0.238、7 簇；Zero 最终 ACC 0.326、NMI 0.041、ARI 0.011、4 簇。完整数据宽结构最终 ACC 0.448、NMI 0.273，说明宽结构本身也需要校准，不能直接当作上界。

这些结果支持后续优先研究“缺失属性填充与训练稳定性”，而不是直接扩大随机重复次数。

## AMGC 独立环境与冒烟

独立环境：`envs/amgc_cpu/`。它继承现有 CPU 科学包以避免重新下载 PyTorch，新增 `torch-geometric==2.6.1`、`xxhash==3.5.0`、`munkres==1.1.4` 只安装在该环境。`pytorch` 原环境中没有这些新增包。`pip check` 报告的是继承环境中已有的历史包版本冲突，不是本次安装新增依赖的导入失败；GCNConv 前向/反向和 negative sampling 冒烟均通过。

工作副本：`amgc_work/`，原始快照 `references/amgc_source/AMGC-master/` 未修改。运行脚本：`run_amgc_stage3.py`。配置为观测比例 0.4（缺失 60%）、split seed 72、model seed 0、edge mask 0.5、20 epoch，学习率余弦调度仍使用官方 1000 epoch 周期。

数据检查全部通过：2708 个节点、10556 条边、1083 个观测节点、1625 个缺失节点；特征、标签、边与本地 Planetoid 数据逐项相等。冷节点 459 个。结果目录为 `amgc_stage3_original_smoke/`。

20 epoch 全部完成，loss 有限，始终占用 7 个簇，峰值进程内存约 550 MB，平均每 epoch 21.27 秒，最终 ACC 0.568、NMI 0.347、ARI 0.283；初始聚类 ACC 0.573、NMI 0.378、ARI 0.296。训练没有崩溃，但 20 epoch 后尚未显示收敛证据，因此不能据此宣称 AMGC 已复现或优于基线。

## AMGC 固定配置 100 epoch 检查

在相同数据掩码、split seed 72、model seed 0 和 edge mask 0.5 下运行 100 epoch，余弦学习率仍按官方 1000 epoch 周期设定。完整日志和逐 epoch 文件保存在 `amgc_stage3_long100/`，控制台日志为 `amgc_stage3_long100.log`。总耗时 1507.5 秒，平均每 epoch 14.44 秒，峰值 RSS 约 586 MB。

最终 ACC 0.6052、NMI 0.3829、ARI 0.3262；初始值分别为 0.5731、0.3776、0.2956。最终仍占用全部 7 个簇，最大簇占比 0.227，最后一次预测变化率降至 0.00037。训练损失全程为有限值；该目标包含互信息项，日志中后期出现负总损失不等于数值错误。后期聚类指标仍缓慢改善，因此判定为“实现稳定、预测趋稳，但未证明完整收敛”。余弦调度到 epoch 100 时学习率仍约为 9.76e-4。

原计划继续相同固定配置至 1000 epoch；CPU 运行后来在第 16 epoch 停止，尚无完整长周期收敛证据。后续检测到本机 GeForce GTX 1650 Ti 有 4 GB 显存，但驱动版本为 457.52；独立 CUDA 环境的 PyTorch 报告 CUDA 可用，却把显存容量识别为 0 MB，任何 CUDA 张量分配均报 `CUDA error: out of memory`。在解决驱动与 CUDA 运行时问题前，不继续耗时的 CPU 1000 epoch 实验，也不启动扩大实验。

## GPU PyTorch 环境检查

独立环境：`envs/amgc_gpu/`，Python 3.8.18、PyTorch 1.8.0、torchvision 0.9.0、CUDA runtime 11.1.1；使用本机离线缓存安装，未更改原 `pytorch` 环境。`torch.cuda.is_available()` 返回 True，设备识别为 GeForce GTX 1650 Ti（计算能力 7.5），但 `get_device_properties(0).total_memory` 返回 0 MB；最小 `torch.ones(1, device='cuda')` 也报 OOM。同期 `nvidia-smi` 显示总显存 4096 MiB、可用约 3 GiB，故不是显存被训练任务占满。此环境当前只能当作安装候选，CUDA 计算验证失败；AMGC 的 PyG 依赖尚未安装。

下一步先更新/核实 NVIDIA 驱动，再按驱动支持范围选择 PyTorch CUDA 版本，重复 CUDA 张量及矩阵乘法测试。通过后才安装与 PyTorch 对应的 PyG 版本，做 AMGC 单 epoch 前向、反向和小批训练；在 GPU 实测每 epoch 耗时与峰值显存后，再决定是否跑满 1000 epoch。

## 下一步门槛

先解决 GPU CUDA 分配错误，完成 AMGC GPU 冒烟和固定配置长周期曲线；同时对 SDCN 的 Zero 塌缩进行填充或损失诊断，并保留最终 epoch、原始预测、全局 Hungarian 评估和独立掩码。只有当 loss、簇占用和后期指标稳定，且至少一个可用填充方法不再发生持续塌缩，才启动多掩码、多种子正式实验。

复核文件：`stage3_manifest.json`（排除独立环境目录），`stage3_plan.json`（预注册配置），以及两个结果目录中的 `config.json`、`loss.csv`、`metrics.csv`、`result.json`。
